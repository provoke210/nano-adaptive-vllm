# Qwen3-4B 单卡验证

**已完成：3090 的 24GiB 足够本次 Qwen3-4B FP16 配置。** 纯 Decode 输入复用吞吐提升 **0.44%–1.21%**、端到端 **0.45%–0.70%**（逐场景配对中位数）；40 对 micro 与 18 对 e2e 全为正，全部输出一致。收益小于此前小模型，未解决沿用原调度参数时的延迟不达标问题。

日期：2026-10-22，RTX 3090 24GiB，Qwen/Qwen3-4B，FP16，无 INT8/INT4 量化，CUDA Graph，batch_invariant=True。

## 显存预算与配置

[官方模型](https://huggingface.co/Qwen/Qwen3-4B) 的 [config](https://huggingface.co/Qwen/Qwen3-4B/blob/main/config.json) 为 36 层、32 query heads / 8 KV heads、head_dim=128、hidden=2560、共享 embedding/LM head。权重文件合计 8,044,982,000 bytes（约 7.49GiB，含少量 safetensors 元数据）。
FP16 KV cache 每 token 为 `2 × 36 × 8 × 128 × 2 = 147456 bytes`，即 144KiB。每个 256-token block 占 36MiB。

- 正确性测试使用 64 blocks，KV 2.25GiB。
- micro/profile 使用 192 blocks，KV 6.75GiB，最大并发 32，初始上下文 32/1024。
- e2e 使用 128 blocks，KV 4.50GiB，最大并发 16，token budget=2048、最大模型长度=4096。

权重与 KV 之外还需要激活、CUDA 上下文、Graph、工作区及分配器余量。结论只适用于实测配置，不表示 24GiB 可以容纳任意长上下文/并发。原始权重为 BF16，本轮转 FP16 运行。

## 首轮发现的生命周期问题

首轮独立 HF 对照通过，但同进程反复创建/退出引擎时全套测试出现 4 failed / 129 passed；OOM 时约 23.23GiB 为实际已分配张量。首个 eager 配置通过，之后的加载失败，不是单个 4B 模型本身放不下。

参数的 `weight_loader` 属性持有模块的绑定方法，而模块又持有参数，形成循环引用。旧实现只删除 ModelRunner，未确保这些循环及时回收。小模型没有把该问题充分暴露出来。

修复：`LLMEngine.exit()` 在删除 runner 后注销 atexit 回调、执行循环垃圾回收并释放空闲 allocator cache。计算与调度热路径未修改。新增禁用自动 GC 时的退出回归测试，并在每次真实模型退出后断言存活 GPU 张量回落到原基线附近（容许 64MiB 小缓存）。修复后的 Mac 测试 127 passed / 7 skipped，4B GPU 主机测试 134 passed；首次失败原始记录完整保留。

核心源码由 `b5f8ec7346dbb8484609f3f8fc9f3ce85da9a99a2294687c6adec0f2f0a9c345` 变为 `22e58ad507b4114aabaec47cf37bbe8edbc844e75382c41491c4cada319f59a7`。此前 Qwen3-0.6B、Llama 性能数字属于旧 hash，不能标为本次新代码的重测结果。退出修复后又对这两个模型分别运行 7 项 GPU 回归，均通过。

远端 manifest 原始 hash 为 `4f475cb7ad94aadfe9e51e8c154fed7edcf6f7065ac6cd33b5728183d58b2325`：macOS tar 附带一个非导入的 `._llm_engine.py` AppleDouble 元数据文件，被现有 manifest 的 `rglob("*.py")` 纳入哈希。已用本地源码加该归档元数据精确复现远端 hash；去除元数据后的可执行源码 hash 为上述 `22e58ad...`。`executed-core-source.tar.gz` 冻结了实际参与哈希的文件，`source-provenance.json` 保存解释，审计同时检查两种哈希。

## 正确性与性能方法

- 独立 HF FP32 对照：相同 FP16 舍入后的权重，完整历史 eager 重算；3 个聊天输入和 257/1537-token 随机输入，每个 8 步，共 40 位置。预设 max_abs≤0.15、relative L2≤0.01、argmax 不同数=0。记录真实 argmax 后沿参考 token 延续相同历史。
- 跨调度自由生成：3 seeds × 5 配置 × 24 请求，共 360 次执行；每次输出 64–128 token，不做 teacher forcing。
- micro：batch=1/4/16/32 × context=32/1024，5 对重复，计时 96 个 Decode 步；先首个输出和 16 步预热。
- profile：batch=1/16/32 × context=32/1024，1 对，计时 48 步，仅作机制分析。
- e2e：mixed/burst/pressure × seeds 101/307，3 对重复，每次 24 请求；固定预算 2048 加现有相同准入（wait=100ms、target=800ms、max_slots=4）。
- 性能 A/B 随机顺序，正式计时关闭 profiling，两组同一核心源码、trace、KV blocks 与调度参数，只切换输入复用开关。比较对象为同一 fork，不是未经修改的上游 nano-vLLM。
- 为适应更大的 KV cache，本轮 micro/profile 最大 batch 与缓存容量不同于之前小模型，且部分合成 prompt 随 case 编号变化；不宣称跨模型全部实验计划/trace 完全相同。

## 正确性最终结果

- 4B 测试：134 passed / 0 skipped / 0 failed，含反复加载后的显存释放断言。
- 独立 HF：40 个比较位置，max_abs=0.060980，max_relative_L2=0.004638，greedy token 不同数=0，预设精度门槛全部通过。logits 非逐位完全相等，参考权重与引擎同为 FP16 舍入后的值。
- 跨调度自由生成：15 轮、360 次请求执行，逐 token 相同。本组抢占为 0，不作高抢占压力覆盖声明。
- 输入复用：80 次 micro + 36 次 e2e + 12 次 profile = 128 次运行全部输出一致；e2e 合计 864 次请求执行。
- 公共退出修复的回归：Qwen3-0.6B、Llama-3.2-1B 分别 7 项 GPU 测试通过。
